# MultiHopper Swarm for Hire

[Swarm for Hire](https://business.multihopper.com/near-swarm/) · [Workspace](https://multihopper-swarm-for-hire.pages.dev/near-swarm) · [API capabilities](https://multihopper-swarm-for-hire.pages.dev/near-swarm/api) · [Service health](https://multihopper-swarm-for-hire.pages.dev/near-swarm/api/health)

**Live capabilities.** Customers connect a Solana wallet to create, inspect or close a work order. A NEAR account signs its job ID and the same payment terms using NEP-413. We verify the account’s finalized full-access key. The resulting link identifies the account-authorized job in our database. An independent NEAR mainnet contract does not attest to job completion.

**Payments.** The customer signs the invoice ID, agent address, gross SOL charge and minimum net payment. The workspace checks the per-payment limit, reserves the amount against the job budget and creates a quote through the authenticated MultiHopper API. A repeat uses the same external reference. A separate approval limits additional account and network costs. Supported Wallet Standard wallets sign the prepared transactions. The workspace saves the exact signed transaction before sending and reconciles its signature on retry.

**Settlement and recovery.** We verify the finalized agent balance increase, the orchestrator debit and the configured MultiHopper screener’s signature for that specific creator and recipient. At reconciliation we reverify the saved customer signatures for the work order, the NEAR job link and the invoice. A signed notification triggers that independent check. Each confirmed signature can settle only one invoice. Recovery matches every transaction against the previously prepared messages. The recovery receipt reports the actual credit, which can include account rent. Reading a job returns its NEAR binding and its recent invoice receipts. The screening evidence comes from the MultiHopper screener. TRM does not issue a separate signature through this integration.

**Release status — November 18.** A live Solana invoice payout and its NEAR settlement receipt are finalized. The agent received 0.002487562 SOL. The workspace supports saved-job resume, signed transaction batches, automatic recovery verification, controlled workspace stop and opt-in revocable receipt links. A healthy funded production route still cannot be cancelled on demand through this integration. Live failed-route refund and full-flow recording remain outstanding. See [API reference](API.md) and `LIVE-DEMONSTRATION.md` for evidence, exact limitations and reproduction steps.

**Two-chain test — November 17.** The new `contract/` registry ran on a real local NEAR node alongside a local Solana validator and the supplied MultiHopper orchestrator. The website gateway created an owner-bound NEAR job, reserved two invoices and verified a finalized payout of 4,999,990 synthetic lamports and a separate recovery credit of 7,999,990 synthetic lamports. The recovery included 3,000,000 lamports already in the fixture account; it is not a principal-only amount. The gateway published authenticated settlement records to NEAR, restarted the node, retried without a second issuance, and closed the job through the same API. The Solana quote/preparation service and screening signer were synthetic fixtures. This is not a live payout/refund or a mainnet stress test.

**NEAR integration activation.** Our dedicated deployed contract is `9bf2f9014058da04b48e6010929fd3045f5507a452ec9acaa8b0a44c42531a0d`; the pinned executable hash is `2ziwpNEyFnCCLt63hxD8BEgJvFPe5GwcLGk5D2gRvzss`. Other installations must configure their own `SWARM_NEAR_CONTRACT`, `SWARM_NEAR_CODE_HASH` (base58 SHA-256 of WASM), `SWARM_NEAR_PUBLISHER_KEY` (32-byte Ed25519 public key, base64) and dedicated server secret `SWARM_NEAR_PUBLISHER_PRIVATE_KEY` (PKCS8 base64). Initialize the contract with that publisher and network `mainnet` in the same transaction as deployment. Use a dedicated contract account, never overwrite an existing user's wallet code. The gateway pins the network, executable, publisher and storage pricing before enabling payments. The receipt key is separate from all funded account keys.

The contract records immutable job terms, per-payment and total limits, customer/agent authorization, invoice reservations and final settlement commitments. Payment principal stays in the existing Solana route. NEAR attached deposits cover storage: 0.01 NEAR per new job and 0.02 per new invoice. They are retained storage contributions, not an agent's spending principal. A repeated invoice cannot expand its budget; a repeated terminal receipt cannot release a reservation twice. Both paid and refunded invoices consume their original authorization so an old invoice cannot be reused. A closed job can still record an already reserved payout or refund.

The publisher verifies finalized Solana receipt contents, exact signed work-order/invoice terms, route-specific recovery messages and the configured screening proof before signing a NEAR receipt. NEAR verifies the publisher signature. This is an authenticated MultiHopper attestation, not a trustless Solana light client and not a TRM-signed certificate. The browser uses the published Meteor web-wallet messaging protocol; MyNearWallet was removed following its sunset notice. No external wallet SDK is loaded into the page. Wallet-returned transaction hashes are independently verified before explorer links are shown.

**Reproduce.** From the repository root run `node --test research/near-swarm-hackathon/*.test.* research/near-swarm-hackathon/site/*.test.mjs research/near-swarm-hackathon/ops/*.test.mjs`. For the two-chain exercise, run `node research/near-swarm-hackathon/test-fixtures/settlement-chains.mjs` with loopback-only networking and the local NEAR sandbox described below. Set `SYNTH_ORCHESTRATOR` to a reviewed compiled orchestrator, `SOLANA_WEB3_MODULE` to the installed Solana web3.js library and `SOLANA_VALIDATOR` to the local validator executable. The public repository contains the integration and test harness. The core program binaries are supplied by the operator.

**Hosting.** Use a dedicated Cloudflare Pages project with a dedicated D1 binding named `SWARM_JOBS`. Apply `site/schema.sql` and `site/settlement.sql`. Store the dedicated `SWARM_SOLANA_API_KEY` as a server secret and set `SWARM_PROVIDER_AUTHORITY` to its public Solana authority. When registration returns its public account address, set `SWARM_PROVIDER_PDA` for a direct lookup on RPCs that restrict program scans. The app checks the finalized provider account and the upstream API checks registration and rewards-wallet rent. Use a dedicated signed notification subscription for the absolute URL in `site/notifications.mjs`. A separately provisioned `SWARM_HOOK_SECRET` can be set as a server secret. Our hosted instance stores its encrypted callback credential in the dedicated database. Renew the callback credential when rotating its encryption key. Build with `node site/build.mjs <output-file>` from this directory. Older signed work orders are bound to their original website origin.

### Activating mainnet settlement

The service operator completes MultiHopper provider registration with the integration authority, selects its rewards wallet and confirms the registration transaction through the self-service API. The authority must have enough SOL to create the provider account and pay the network fee. The configured rewards wallet must retain the network’s rent-exempt balance. At the November 17 RPC check, the 96-byte provider account required 1,137,920 lamports and a zero-data rewards wallet required 650,240 lamports. These are balances to maintain, distinct from fees. Query the current minimum at activation.

Use the resulting live key for the dedicated workspace, bind its public provider account address and verify the notification credential after a key rotation. The health endpoint reports API authentication and notification availability. The capabilities endpoint shows whether funded payment and recovery are open. The upstream API rechecks the provider and rewards wallet when preparing each payment. [MultiHopper provider registration](https://multihopper.com/self-service)

## Local development server

The following commands exercise the earlier loopback-only research server. The published workspace uses the implementation in `site/` described above.

Run `node server.mjs` and open http://127.0.0.1:18988. Connect an injected Solana wallet and sign a login message, or use the demo account. Create a synthetic job, issue an agent payment and fail the job to recover its remaining balance. Run `node --test engine.test.cjs` for the model regression.

The local server binds to loopback. All amounts are positive integer synthetic units. State is in memory and resets on restart.

- POST /api/jobs with `{"jobId":"job1","budget":"100","limit":"25"}`.
- POST /api/payments with `{"jobId":"job1","invoiceId":"inv1","amount":"20"}`.
- POST /api/recover with `{"jobId":"job1"}`.

The local API verifies an origin-bound, expiring Solana wallet message signature before assigning a wallet session. Challenges are single-use and the number of pending challenges and sessions is bounded. Without a wallet it uses the shared synthetic demo identity. The in-memory mode is a simulation and resets on restart. The wallet session uses a local HTTP-only cookie and exists only in the current process. This is not a production authentication service: public deployment needs durable session management, HTTPS cookie configuration, rate limits and a proper security review.

The local NEAR mode uses a disposable, loopback-only NEAR sandbox, the existing policy contract and synthetic ordinary-token grant provider. On macOS after restoring the reviewed dependencies and building the WASM through `python3.12 research/hub/near/run.py`, start it from the repository root:

```sh
sandbox-exec -f research/hub/near/sandbox/local-only.sb env DEMO_NEAR=1 PORT=18990 PATH=/usr/bin:/bin:/opt/homebrew/bin node research/near-swarm-hackathon/server.mjs
```

Open http://127.0.0.1:18990. The local mode supports two mapped synthetic customer identities and automatically mints synthetic units. Jobs and wallet-to-synthetic mappings are process-local. If a creation is interrupted, its ID remains blocked as unknown until the disposable instance is restarted. It is not a durable recovery service. Existing payment and recovery operations use the NEAR research coordinator.

Run `env DEMO_TEST_BASE=http://127.0.0.1:18990 node --test research/near-swarm-hackathon/api.test.mjs` against a fresh local instance. The test creates two disposable wallet key pairs, proves control of each, rejects challenge replay and cross-customer requests, checks duplicate and concurrent requests and recovers synthetic balances.

The optional Solana status reader is exposed through the UI and the local API when both `MH_SOLANA_TEST_API_URL` and `MH_SOLANA_TEST_API_KEY` are configured. Only an `mh_test_` key is accepted. A signed wallet session may see only a matching test transfer it owns; route details and recipients are not returned by the demo gateway. Integration tests use a mock server: no actual MultiHopper API has been called. This read-only lookup does not create, authorize or settle transfers, and does not perform or verify TRM screening.

`solana-execution-client.mjs` implements a devnet-only server-side API client for estimates, transfer creation, preparation, status, confirmation and rescue. It requires test credentials, a wallet owner and a durable single-host operation journal. Before making a write, the journal records the request as uncertain; a lost response or interrupted process blocks a duplicate until the operation is reconciled. A recorded API response is not evidence of on-chain finality. Tests use a mock transport; the client does not sign or broadcast transactions. It is not yet wired to the job workflow, a wallet transaction reviewer, a production-grade distributed journal, an operational reconciliation path, or a verified cross-chain custody model. Test credentials alone do not prove that TRM screening is enabled in a particular environment.

The loopback server keeps its NEAR jobs and Solana adapter in separate test environments. Use it with synthetic funds. For signed job links and finalized Solana receipts, use the hosted workspace implementation in `site/`.

`solana-live-client.mjs` is an isolated, mock-tested production API adapter. It requires a configured HTTPS origin, live API key, authenticated wallet owner and operation journal; it rejects responses belonging to a different source or test mode. It is not wired into the browser or job lifecycle, and it cannot independently verify unsigned transaction contents, TRM enforcement or on-chain settlement. Do not use it for live funds until those gates are implemented and reviewed.

`payment-control.mjs` is a local research coordinator for binding an owner-approved, immutable job plan to an agent, recipient, mint, budget and per-payment limit. It persists customer-scoped plans, reserves budget before requesting a quote, rejects duplicate invoices across the customer's jobs, blocks ambiguous requests, verifies returned quote fields, and freezes a job before recovery. Its SQLite state is single-host and its agent and owner inputs must be authenticated by a future caller. It does not hold funds, verify on-chain grants or finality, execute payments or recover principal; frozen reservations require reconciliation. `job-solana-integration.test.mjs` tests the coordinator and production API adapter together using a mock transport only.

The production API adapter can prepare and confirm rescue for a failed, owner-checked transfer. `wallet-execution.mjs` tests ordered wallet handoff, whole-bundle pre-inspection and lost-response handling using mock wallet, transaction inspector and RPC interfaces. It has no real inspector, wallet binding or RPC adapter and is not exposed by the server. An API rescue response or mock confirmation is not proof that funds were recovered; canonical receipts and balance reconciliation are still required.

`screening-proof.mjs` verifies a signed `MHC:v1:hops` proof against a supplied trusted signer, program, route, creator and ordered recipient set. The caller must independently verify that the signer came from the correct on-chain compliance configuration and that the proof covers the full route. This validates a MultiHopper screener signature, not a TRM-authenticated attestation; extra screening addresses are not bound by this proof. It is not wired to live screening or settlement.

`screening-from-chain.mjs` combines the proof verifier with a finalized RPC read of the compliance signer and rejects disabled screening, wrong network, wrong owner and malformed configuration data. The program, configuration PDA and network genesis must be independently pinned by the operator; the module does not derive or establish those values. Tests use synthetic keys and an RPC mock, not a live screener or production RPC.

When explicitly enabled with `MH_LIVE_ENABLED=1` and all four `MH_LIVE_DB_PATH`, `MH_LIVE_API_URL`, `MH_LIVE_API_ORIGIN` and `MH_LIVE_API_KEY` settings, the loopback server exposes wallet-authenticated `/api/live/jobs`, `/api/live/quote`, and `/api/live/freeze` endpoints. These are manual owner-initiated plans and quotes, not funded NEAR jobs or autonomous agent grants. The live configuration is off by default; no real API calls have been made. Transaction preparation is deliberately not exposed until independent transaction validation and safe recovery are implemented. The adapter cannot prove TRM is enabled; do not treat a quote as a screening result or use this research service with real funds.
